# FEBAMA

A small `gsm.febama` submodule that ports the R package `febama` as an application layer over the current Python GSM core.

Status as of 2026-05-13: the first Python FEBAMA slice is implemented. The
current code supports precomputed LPD/features, MAP fitting of softmax gating
coefficients, a predictive-distribution registry, basic and optional base
forecasters, `tsfeatures`-based feature extraction, feature cleaning/scaling,
CSV feature-table loading, rolling-origin LPD/feature construction, one-step
and recursive multi-step forecasting/metrics, and a minimal runnable example
script.

## Package Summary

`gsm.febama` is a Python package for feature-based Bayesian forecast model averaging.
It combines predictive distributions from several base forecasters with
time-varying softmax weights. The softmax linear predictors depend on time
series features. With `m` base forecasters, FEBAMA estimates `m - 1` weight
regressions and keeps the last forecaster as the baseline component. The R code
mostly scores Gaussian predictive distributions from forecast means and
standard deviations; the Python design should make that distribution choice
pluggable.

Important source files:

| R file | Purpose |
| --- | --- |
| `R/api.R` | Public workflow: config, compute features, fit, forecast, summarize. |
| `R/default_parameters.R` | Legacy default nested config list. |
| `R/densities_features.R` | Rolling historical log predictive densities and THA feature matrices. |
| `R/models.R` | Base forecaster wrappers: ETS, ARIMA, naive, drift, GARCH, EGARCH, realized GARCH, SV. |
| `R/logscore.R` | FEBAMA objective: logsumexp of feature weights plus model log predictive densities. |
| `R/priors.R` | Normal coefficient priors and beta/Bernoulli feature-selection priors. |
| `R/posterior.R` | Log posterior and gradients. |
| `R/mcmc.R` | MAP/BFGS, SGLD, and variable-selection updates. |
| `R/forecast.R` | Recursive forecast combination, weights, log score, MASE, SMAPE. |
| `inst/examples/sp500*.R` | S&P 500 paper example and MAP/SGLD comparison scripts. |
| `tests/testthat/` | Useful migration acceptance tests. |

Bundled data/schema examples:

- `data/sp500_daily_percent_log_returns.csv`: `date, close, log_return`.
- `data/sp500_features_table3.csv`: rolling origin index/date, next return, and
  the 15 stock-market features used in the paper.
- `data/sp500_map_sgld_comparison_fast.csv`: fast-mode MAP/SGLD output fixture.

## Core Model Mapping

The FEBAMA likelihood is a mixture-of-experts gating problem where component
log densities are supplied externally or computed from a selected predictive
distribution:

```text
theta[t, j] = predictive parameters from forecaster j
lpd[t, j] = log p_distribution_j(y_t | theta[t, j])
eta[t, j] = x_t beta_j, for j = 1, ..., m - 1
eta[t, m] = 0 baseline
log w[t, :] = eta[t, :] - logsumexp(eta[t, :])
objective = sum_t logsumexp(log w[t, :] + lpd[t, :])
```

This belongs in `gsm.febama` rather than in `gsm.models`, because the expert
distributions are generated by external forecasting models instead of a single
GSM distribution kernel. The gating layer must not assume Gaussian experts.

## Distribution Choice

FEBAMA should be able to choose any appropriate component distribution as long
as the distribution implementation provides a small common interface:

```python
class PredictiveDistribution:
    name: str
    params: Mapping[str, np.ndarray]

    def log_prob(self, y) -> np.ndarray: ...
    def mean(self) -> np.ndarray: ...
    def variance(self) -> np.ndarray: ...
```

Implementation uses a lightweight registry instead of branching
throughout the application:

```python
register_distribution("gaussian", GaussianPredictive)
register_distribution("studentt", StudentTPredictive)
register_distribution("splitnormal", SplitNormalPredictive)
register_distribution("splitt", SplitTPredictive)
```

Start with distributions already available in `gsm.models` when possible:

| FEBAMA distribution | Parameters | Backing implementation |
| --- | --- | --- |
| `gaussian` | `mean`, `sd` or `variance` | default R-compatible scoring path. |
| `studentt` | `mean`, `scale`, `df` | `gsm.models.studentt` density formula. |
| `splitnormal` | `mean`, `sigma`, `skewness` | `gsm.models.splitnormal`. |
| `splitt` | `mean`, `df`, `scale`, `skewness` | `gsm.models.splitt`. |
| `lognormal` | `mean`, `scale` plus parameterization | `gsm.models.lognormal`. |
| `gamma` | `mean`, `variance` or `shape`, `scale` | `gsm.models.gamma`. |
| `poisson` and counts | distribution-specific count parameters | only when the response is discrete. |

Implemented status:

- `PredictiveDistribution(name, params)` is the common object returned by base
  forecasters.
- `gsm.febama.distributions` provides the registry and `log_prob_matrix(...)`.
- Registered distributions currently include `gaussian`, `studentt`,
  `splitnormal`, `splitt`, `lognormal`, `gamma`, and `poisson`.
- Base forecasters return Gaussian `PredictiveDistribution` objects for the
  current examples.

Remaining design rule: new forecasters should return a
`PredictiveDistribution` object, not only `(mean, sd)`.

## Proposed Python Layout

Keep the submodule small and data-source agnostic:

```text
gsm/febama/
  __init__.py
  config.py          # FebamaConfig and structural validation
  data.py            # SeriesData and LpdFeatures containers
  distributions.py   # predictive distribution registry and log_prob adapters
  forecasters.py     # naive, drift, optional statsforecast/arch adapters
  features.py        # feature extraction and feature cleaning/scaling
  scoring.py         # JAX logscore, softmax weights, predictive score utilities
  inference.py       # MAP first, then mean-field VB over gating coefficients
  forecast.py        # recursive combination, MASE, SMAPE, log score summaries
  api.py             # public workflow wrappers matching the R API shape
```

Current implemented files:

```text
gsm/febama/
  __init__.py
  api.py
  config.py
  data.py
  distributions.py
  features.py
  forecast.py
  forecasters.py
  inference.py
  scoring.py
```

`forecast.py` currently implements recursive forecasting with per-horizon
features, weights, component predictions, and optional VB sampled outputs.

Do not put fixed data paths into config. Example scripts should accept `--data`
and config objects should only describe model structure and fitting choices.

### Phase 2: Inference for Gating Coefficients - Partial

1. Implement MAP as a parity baseline.
   - Use `scipy.optimize.minimize` with gradients from JAX.
   - Match R `optimize_map_coefficients()` behavior for active coefficients.
2. Implement mean-field Gaussian VB using existing `gsm.vi.engine` patterns.
   - Variational posterior over the `m - 1` gating coefficient blocks.
   - Objective is expected log score plus Gaussian coefficient prior.
   - Use `optax` and posterior sampling like the existing GSM models.
3. Replace explicit R-style variable-selection Gibbs as follows:
   - first: optional ARD shrinkage for feature columns;
   - later: optional Bernoulli/Beta indicator approximation if needed.

Acceptance tests:

- MAP keeps all features active when variable selection is disabled.
- MAP only updates active coefficients in a synthetic active-mask test.
- VB returns finite ELBO/objective history and posterior-sampled weights.

## Risks and Decisions

- Exact R `tsfeatures` parity is expensive. Python now uses the installed
  `tsfeatures` package through a narrow adapter, but paper-level replication
  still needs a column-by-column parity check against the R THA feature output.
- R `forecast`, `rugarch`, `highfrequency`, and `stochvol` do not map one-to-one
  to Python. Keep these optional and separate from the core FEBAMA kernel.
- Some distributions are only appropriate for certain response supports. The
  config should validate continuous real, positive, or discrete responses before
  fitting.
- The original R code has MAP/SGLD plus variable-selection indicators. The
  Python GSM direction is VB, so explicit indicator sampling should not be the
  first migration target. Use ARD first.
- The target should not copy fixed data paths from the R examples. Data paths
  belong in scripts and tests, not in config dataclasses.
